Stochastic Optimization for Supply Chains: A Small, Tested Example

A small, tested example of Bayesian demand updating and an order-up-to rule, with its assumptions stated

April 13, 2026 · Ahmad Faruqi · 13 min read

In brief

  • What this is. A small, complete, tested Python example (standard library only) that updates a demand estimate with Bayesian inference, turns the posterior into an order-up-to level, and checks the policy in a simulation.
  • What it is not. It is not a production system and it does not implement robust optimisation. It makes strong assumptions (one item, i.i.d. normal demand, backorders, linear costs) that are listed below.
  • Evidence. The tests check arithmetic and inventory bookkeeping. We have not benchmarked accuracy, runtime or savings, and we make no such claims.

Stochastic Optimisation in One Paragraph

Deterministic planning plugs one forecast into an optimisation model. Stochastic optimisation treats demand (and sometimes supply) as random and chooses decisions that perform well on average or against a chosen risk measure. The simplest case in supply chains is the newsvendor-style rule used here: order up to the level at which the probability of covering demand equals a ratio set by the cost of shortage and the cost of excess stock.

The Problem and Its Assumptions

  • One item at one location, reviewed every period, with an integer lead time of L periods.
  • Per-period demand is independent and identically distributed Normal(μ, σ²), with unknown μ and σ². Real demand is often trending, seasonal, intermittent or skewed; this example ignores all of that, and negative demand is only a limitation of the normal model.
  • Unmet demand is backordered, so on-hand stock can go negative. Costs are linear, in currency per unit per period: holding_cost on stock on hand and shortage_cost on backorders, both charged on end-of-period stock.
  • No fixed ordering cost, capacity limit, minimum order quantity or supplier failure.

Under these assumptions the classical base-stock result (see Zipkin, Foundations of Inventory Management, 2000) says the best order-up-to level for inventory position (on hand plus on order) is the quantile of demand over L + 1 periods at the critical ratio shortage_cost / (shortage_cost + holding_cost).

The Code

Save this as bayes_inventory.py. It uses only the Python standard library. We ran it and its tests on Python 3.14 only; we have not tested older versions.

"""Educational example: Bayesian demand updating, a base-stock rule and an inventory simulation.

Standard library only. It is a teaching sketch, not a production system.

Assumptions (all of them are simplifications):
  * one item, one location, periodic review, integer lead time in periods
  * per-period demand is i.i.d. Normal(mu, sigma^2) with unknown mu and sigma^2
  * unmet demand is backordered (negative on-hand stock)
  * linear costs, in currency per unit per period: holding_cost and shortage_cost
  * no fixed ordering cost, no capacity limits, no supplier failures
"""
import math
import random
from dataclasses import dataclass


@dataclass(frozen=True)
class Posterior:
    """Normal-Inverse-Gamma parameters for (mu, sigma^2)."""
    mu: float
    kappa: float
    alpha: float
    beta: float


# Hypothetical, weak prior used for illustration. Replace it with your own and test how much it matters.
DEFAULT_PRIOR = Posterior(mu=100.0, kappa=1.0, alpha=2.0, beta=100.0)


def clean_demand(observations):
    """Return usable demand values.

    None and NaN mean "not observed" and are dropped. 0 means "demand was confirmed to be zero"
    and is kept. Negative or infinite values are errors, not data.
    """
    cleaned = []
    for x in observations:
        if x is None or (isinstance(x, float) and math.isnan(x)):
            continue
        if not math.isfinite(x) or x < 0:
            raise ValueError(f"invalid demand value: {x!r}")
        cleaned.append(float(x))
    if not cleaned:
        raise ValueError("no usable demand observations")
    return cleaned


def update(prior, observations):
    """Conjugate update of the Normal-Inverse-Gamma posterior."""
    xs = clean_demand(observations)
    n = len(xs)
    x_bar = sum(xs) / n
    ss = sum((x - x_bar) ** 2 for x in xs)
    kappa_n = prior.kappa + n
    return Posterior(
        mu=(prior.kappa * prior.mu + n * x_bar) / kappa_n,
        kappa=kappa_n,
        alpha=prior.alpha + n / 2,
        beta=prior.beta + 0.5 * ss + prior.kappa * n * (x_bar - prior.mu) ** 2 / (2 * kappa_n),
    )


def expected_variance(post):
    """Posterior mean of the per-period demand variance sigma^2 (needs alpha > 1)."""
    if post.alpha <= 1:
        raise ValueError("posterior mean of the variance is undefined for alpha <= 1")
    return post.beta / (post.alpha - 1)


def mean_scale2(post):
    """Squared scale of the Student-t posterior of the demand MEAN: uncertainty about the parameter."""
    return post.beta / (post.alpha * post.kappa)


def predictive_params(post, periods=1):
    """Student-t posterior predictive of total demand over `periods` periods: (df, loc, scale^2).

    It includes both parameter uncertainty and ordinary demand noise, so it is wider than mean_scale2.
    """
    scale2 = (post.beta / post.alpha) * (periods + periods ** 2 / post.kappa)
    return 2 * post.alpha, periods * post.mu, scale2


def sample_predictive_sum(post, periods, n, rng):
    """Draw n samples of total demand over `periods` periods from the posterior predictive."""
    out = []
    for _ in range(n):
        sigma2 = post.beta / rng.gammavariate(post.alpha, 1.0)  # Inverse-Gamma(alpha, beta)
        mu = rng.gauss(post.mu, math.sqrt(sigma2 / post.kappa))
        out.append(rng.gauss(periods * mu, math.sqrt(periods * sigma2)))
    return out


def base_stock_level(post, lead_time, holding_cost, shortage_cost, n=200_000, seed=1):
    """Order-up-to level S for inventory position (on hand + on order).

    With backorders and linear costs, the classical base-stock result sets S at the critical-ratio
    quantile q = shortage_cost / (shortage_cost + holding_cost) of demand over lead_time + 1 periods.
    Here that demand is the Bayesian predictive, estimated by sampling (seeded, so it is repeatable).
    """
    if lead_time < 0 or int(lead_time) != lead_time:
        raise ValueError("lead_time must be a non-negative integer")
    if holding_cost <= 0 or shortage_cost <= 0:
        raise ValueError("costs must be positive")
    q = shortage_cost / (shortage_cost + holding_cost)
    samples = sorted(sample_predictive_sum(post, lead_time + 1, n, random.Random(seed)))
    return max(0.0, samples[min(n - 1, int(q * n))])


def simulate(base_stock, demands, lead_time, initial_on_hand, holding_cost, shortage_cost):
    """Run the base-stock policy against given demands. Returns (rows, totals).

    Each period: (1) orders due this period arrive, (2) order up to base_stock, (3) demand occurs,
    (4) costs are charged on end-of-period stock. An order placed in period t arrives in period t + lead_time.
    """
    arrivals = {}
    on_hand = float(initial_on_hand)
    on_order = 0.0
    rows = []
    total_holding = total_shortage = 0.0
    for t, d in enumerate(demands):
        start = on_hand
        received = arrivals.pop(t, 0.0)
        on_hand += received
        on_order -= received
        order = max(0.0, base_stock - (on_hand + on_order))
        if order:
            if lead_time == 0:
                on_hand += order
            else:
                arrivals[t + lead_time] = arrivals.get(t + lead_time, 0.0) + order
                on_order += order
        on_hand -= d
        holding = holding_cost * max(on_hand, 0.0)
        shortage = shortage_cost * max(-on_hand, 0.0)
        total_holding += holding
        total_shortage += shortage
        rows.append({"t": t, "start": start, "received": received, "order": order, "demand": d,
                     "end": on_hand, "holding": holding, "shortage": shortage})
    totals = {"holding": total_holding, "shortage": total_shortage, "total": total_holding + total_shortage}
    return rows, totals

What each part does

  • Missing versus zero demand. clean_demand drops None and NaN (not observed) but keeps 0 (confirmed zero demand). Treating a missing day as zero would pull the estimate down, so the two are never mixed. Negative or infinite values raise an error, and so does an empty input.
  • Bayesian update. update applies the conjugate Normal-Inverse-Gamma update. The prior in DEFAULT_PRIOR is hypothetical and weak; with little data it matters a lot, so replace it with your own and check how sensitive the result is.
  • Parameter uncertainty versus predictive uncertainty. mean_scale2 describes uncertainty about the average demand, which shrinks as data accumulates. predictive_params describes uncertainty about future demand, which also includes ordinary demand noise, so it is always wider. Safety stock must cover the predictive spread, not just the uncertainty about the mean.
  • Base-stock level. base_stock_level samples the predictive distribution for L + 1 periods and takes the critical-ratio quantile. Sampling is seeded, so results are repeatable.
  • Simulation. simulate records, for each period, starting stock, arrivals, the order placed, demand, ending stock and the two cost components, so the inventory balance can be checked by hand.

A Hand-Checkable Example

Using the hypothetical prior (μ₀ = 100, κ₀ = 1, α₀ = 2, β₀ = 100) and four observed demands 90, 110, 100 and 100:

  • n = 4, sample mean 100, sum of squared deviations 200.
  • κ = 1 + 4 = 5; μ = (1 × 100 + 4 × 100) / 5 = 100; α = 2 + 4/2 = 4; β = 100 + 0.5 × 200 + 0 = 200.
  • Expected variance = β / (α − 1) = 200 / 3 ≈ 66.7 per period squared.
  • Uncertainty about the mean: scale² = β / (α κ) = 200 / (4 × 5) = 10. Predictive demand for one period: scale² = (β / α)(1 + 1/κ) = 50 × 1.2 = 60, with 2α = 8 degrees of freedom.
  • For a lead time of 2 periods the demand cover is 3 periods: location 3 × 100 = 300 and scale² = 50 × (3 + 9/5) = 240. With holding cost 1 and shortage cost 9 the critical ratio is 9 / 10 = 0.9, the Student-t (8 degrees of freedom) 0.90 quantile from standard tables is 1.3968, and the order-up-to level is about 300 + 1.3968 × √240 ≈ 321.6.

The simulation can be checked by hand as well. With demand of 10 per period, a lead time of 2 and an order-up-to level of 30 (exactly three periods of demand), ending stock is 20, 10, 0, 0, 0 over five periods and the holding cost is 30 with no shortage. Lowering the level to 20 gives ending stock of 10, 0, −10, −10, −10: a holding cost of 10 and 30 backordered unit-periods at a shortage cost of 5, a total of 160.

The Tests

Save this as test_bayes_inventory.py in the same folder and run python -m unittest. The tests reproduce the hand calculations above, check that missing values do not change the posterior, check invalid inputs, and verify the inventory balance and unit conservation in a randomised simulation. We also deliberately broke the predictive-scale formula and the arrival timing to confirm the tests fail when the code is wrong.

import math
import random
import unittest

import bayes_inventory as bi


class CleanDemand(unittest.TestCase):
    def test_missing_dropped_zero_kept(self):
        self.assertEqual(bi.clean_demand([0, None, float("nan"), 5]), [0.0, 5.0])

    def test_empty_and_all_missing_raise(self):
        with self.assertRaises(ValueError):
            bi.clean_demand([])
        with self.assertRaises(ValueError):
            bi.clean_demand([None, float("nan")])

    def test_invalid_values_raise(self):
        for bad in (-1, float("inf")):
            with self.assertRaises(ValueError):
                bi.clean_demand([10, bad])


class Posterior(unittest.TestCase):
    # Hand calculation: n=4, mean 100, sum of squares 200, prior (100, 1, 2, 100)
    # kappa=5, mu=100, alpha=4, beta=100 + 0.5*200 + 0 = 200
    post = bi.update(bi.DEFAULT_PRIOR, [90, 110, 100, 100])

    def test_update_matches_hand_calculation(self):
        self.assertAlmostEqual(self.post.mu, 100.0)
        self.assertAlmostEqual(self.post.kappa, 5.0)
        self.assertAlmostEqual(self.post.alpha, 4.0)
        self.assertAlmostEqual(self.post.beta, 200.0)

    def test_expected_variance(self):
        self.assertAlmostEqual(bi.expected_variance(self.post), 200 / 3)

    def test_parameter_uncertainty_is_narrower_than_predictive(self):
        self.assertAlmostEqual(bi.mean_scale2(self.post), 10.0)        # 200 / (4 * 5)
        df, loc, scale2 = bi.predictive_params(self.post, 1)
        self.assertAlmostEqual(scale2, 60.0)                          # (200 / 4) * (1 + 1/5)
        self.assertEqual((df, loc), (8.0, 100.0))
        self.assertGreater(scale2, bi.mean_scale2(self.post))

    def test_missing_values_do_not_change_the_posterior(self):
        with_gaps = bi.update(bi.DEFAULT_PRIOR, [90, None, 110, 100, float("nan"), 100])
        self.assertEqual(with_gaps, self.post)

    def test_sampled_predictive_matches_student_t_quantile(self):
        # Lead time 2 -> 3 periods: loc 300, scale^2 = 50 * (3 + 9/5) = 240.
        # t(8) 0.90 quantile = 1.3968 (standard table) -> 300 + 1.3968 * sqrt(240) = 321.64
        s = bi.base_stock_level(self.post, lead_time=2, holding_cost=1.0, shortage_cost=9.0)
        self.assertAlmostEqual(s, 300 + 1.3968 * math.sqrt(240), delta=0.5)

    def test_base_stock_is_repeatable_and_validates_inputs(self):
        a = bi.base_stock_level(self.post, 1, 1.0, 4.0, n=5000, seed=7)
        b = bi.base_stock_level(self.post, 1, 1.0, 4.0, n=5000, seed=7)
        self.assertEqual(a, b)
        for args in ((-1, 1.0, 4.0), (1.5, 1.0, 4.0), (1, 0.0, 4.0), (1, 1.0, -1.0)):
            with self.assertRaises(ValueError):
                bi.base_stock_level(self.post, *args)


class Simulation(unittest.TestCase):
    def test_exact_cover_has_no_shortage(self):
        # Demand 10 per period, lead time 2, S = 30 = 3 periods of demand.
        rows, totals = bi.simulate(30, [10] * 5, 2, 30, holding_cost=1.0, shortage_cost=5.0)
        self.assertEqual([r["end"] for r in rows], [20, 10, 0, 0, 0])
        self.assertEqual(totals, {"holding": 30.0, "shortage": 0.0, "total": 30.0})

    def test_too_low_base_stock_creates_backorders(self):
        rows, totals = bi.simulate(20, [10] * 5, 2, 20, holding_cost=1.0, shortage_cost=5.0)
        self.assertEqual([r["end"] for r in rows], [10, 0, -10, -10, -10])
        self.assertEqual(totals, {"holding": 10.0, "shortage": 150.0, "total": 160.0})

    def test_inventory_balance_and_unit_conservation(self):
        rng = random.Random(3)
        demands = [max(0.0, rng.gauss(100, 20)) for _ in range(200)]
        for lead_time in (0, 1, 3):
            rows, _ = bi.simulate(350, demands, lead_time, 350, 1.0, 5.0)
            for r in rows:
                placed_now = r["order"] if lead_time == 0 else 0.0
                self.assertAlmostEqual(r["end"], r["start"] + r["received"] + placed_now - r["demand"])
            ordered = sum(r["order"] for r in rows)
            received = sum(r["received"] for r in rows) + (ordered if lead_time == 0 else 0.0)
            in_pipeline = ordered - received
            self.assertGreaterEqual(in_pipeline, -1e-9)
            self.assertAlmostEqual(rows[-1]["end"], 350 + received - sum(demands))

    def test_empty_demand_gives_empty_result(self):
        rows, totals = bi.simulate(10, [], 1, 5, 1.0, 1.0)
        self.assertEqual((rows, totals["total"]), ([], 0.0))


if __name__ == "__main__":
    unittest.main()

These tests show that the code does what the stated formulas say. They do not show that the policy is good for any real supply chain.

Solvers and Licensing

This example needs no optimisation solver; it uses a closed-form rule and a simulation. If you extend it to a linear or mixed-integer model, you will need one. Commercial solvers such as Gurobi are licensed under the vendor's terms, which differ between commercial, academic and evaluation use, so check the current terms for your situation. Open-source solvers such as HiGHS, CBC and GLPK each have their own open-source licence; check that it suits your use.

What About Robust Optimisation?

Bertsimas and Sim's "The Price of Robustness" (Operations Research 52(1), 2004, pp. 35–53) proposes protecting each uncertain constraint against a limited number of coefficients taking their worst-case values at once; a parameter Γ per constraint sets how many, so the modeller can trade cost against conservatism. The robust counterpart of a linear program stays a linear program, with extra variables and constraints linked to each uncertain constraint. A correct implementation has to include those linking constraints, which is why we do not offer a quick version here. If you need one, work from the paper.

What Published Research Shows, and Its Limits

A November 2025 arXiv preprint by Shahnawaz and Safder proposes a stochastic learning-optimisation model for automotive supply chains and compares a static policy with an adaptive policy that updates its estimates by Bayesian inference. Its abstract reports a 7.4% cost reduction in stable conditions and a 5.7% improvement during supply disruptions. These come from simulations with synthetic data (for example constant demand of 10 per period, a static (s,S) baseline of 25 and 50, 30 replications), and the paper is a preprint. The reported service-level gain of 2.0% is two percentage points (from 93.4% to 95.4%). The authors also report that the approach struggled in a sudden demand shock, where service fell to 77.0% against 93.4% for the baseline, which they attribute to the conservatism of Bayesian updating. Treat these numbers as one simulation study, not as expected results for your business.

An Aston University paper, "An Integrated Robust Optimization and Simulation Framework for Sustainable and Resilient Automotive Supply Chain Management", combines robust optimisation with simulation for automotive supply chains. We did not review it in detail, so we cite it as further reading only.

Where to Go Next

  • Validate first. Compare any policy against your current one on held-out historical periods before trusting it.
  • Relax the assumptions one at a time: trend and seasonality, intermittent demand (many zero periods), non-normal demand, fixed ordering costs and service-level constraints.
  • Extend the structure: several items, several echelons, supplier failures.

Frequently Asked Questions

Is this code ready for production use?

No. It is an educational example with strong assumptions and tests for its arithmetic and bookkeeping, not for real-world performance.

Does it need Gurobi or another solver?

No. It uses only the Python standard library. A solver becomes necessary only if you extend it to a linear or mixed-integer model.

Why does the example use Bayesian updating?

Because demand parameters are unknown and must be estimated from limited data. The Bayesian posterior carries that uncertainty into the order-up-to level. It does not remove the need to check the assumptions, such as stable, independent demand.

What is the difference between parameter uncertainty and demand uncertainty?

Parameter uncertainty is how unsure you are about the true average demand; it falls as data accumulates. Demand uncertainty is the period-to-period randomness that remains even if the parameters were known. Safety stock needs to cover both.

How is missing demand different from zero demand?

A missing observation means the demand was not recorded; it should be left out of the estimate. A zero means demand was observed and was zero; it is information and should be kept.
